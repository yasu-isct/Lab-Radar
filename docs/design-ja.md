# Lab-Radar 設計メモ

[READMEへ戻る](../README.md)

**構想段階の検討案です。以下は現在のAPIが提供する機能や、確定した開発Specではありません。**

## 提供したい情報

| 項目 | 意図 |
| --- | --- |
| 候補の研究室・所属 | どこを調べるべきか分かる |
| 関連するテーマ・手法・研究対象 | 分野名の一致だけにしない |
| その理由を支える記述とURL | 利用者が自分で根拠を確認できる |
| 不一致と未確認事項 | 一致点だけを強調せず、比較を助ける |
| 資料の取得日・版 | 所属や研究内容の古さを確認できる |

既存のProfessorProfileには所属、research_areas、publications、source_urls等があります。一方、上表の全てが現在のschemaで表現できるわけではありません。出典の粒度・取得日時などの契約は、実資料の小規模検証で固めます。

## 検索の考え方

研究計画を丸ごと一つのベクトルにして順位を出すだけでは、「テーマは近いが手法が違う」などの差が見えにくくなります。分野・手法・対象という観点を整理し、候補検索と、出典に基づく関連性の説明を分ける方向を検討します。

ただし、複雑なパイプラインを最初から組む方針ではありません。まずキーワード検索を基準とし、埋め込み検索や再順位付けを追加する価値を測ります。LLMを使った説明だけで検索品質を評価しないようにします。

## 最小検証の案

- 一つの研究分野で10〜20研究室程度の資料と、少数の匿名・合成研究計画を用意する。
- 正式な収集前に、対象サイトの利用条件、取得範囲、出典と更新の扱いを確認する。
- 教務担当者が「候補として有用／関連が弱い／情報不足」を評価するための基準を作る。
- 同じ集合でキーワード検索と埋め込み検索を比較する。必要性が確認できた場合のみrerankingを追加する。
- 候補の上位表示、説明の根拠充足、古い所属・同名教員の混同、時間・APIコストを記録する。

件数は設計上の目安です。データの収集・評価は未実施であり、この文書だけで有料API利用や自動巡回を開始するものではありません。

## J-Gradと共通化するもの

| 共通化を検討 | 専用に設計するもの |
| --- | --- |
| 学校・研究科・専攻の識別情報 | 教員・研究室の識別、異動・改称の扱い |
| 出典を開く画面と参考レポートの導線 | Webページ・論文の取得と更新管理 |
| 資料版・原文・検証記録を保つ考え方 | 研究上の関連性を評価する検索・ランキング |
| 既存の画面構成・API境界 | 研究計画など入力情報の保持・送信範囲 |

募集要項と研究室ページは更新単位も権威の意味も違います。両者を無差別に同じ検索対象へ混ぜず、用途に応じた資料範囲を選ぶ設計を検討します。既存のJ-Grad索引を上書きして実験する方針ではありません。

## 判定しないこと

研究内容の関連性から、教員の受入意思、募集枠、出願資格、合格確率を推定しません。連絡先の提示と連絡代行も別機能です。実装予定として自動メール送信を含めていません。

## 統合を進める判断材料

候補と理由が実際の比較に役立ち、出典を確認でき、単純な検索基準に対する改善を説明できること。その結果を見て、J-Gradの拡張機能として開発範囲を決めます。
